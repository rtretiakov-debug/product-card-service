# Спецификация и требования

## 1. Цель проекта

Разработать локальный прототип сервиса, который по входным данным о контрольно-измерительном приборе создаёт черновик карточки товара для B2B-интернет-магазина. Менеджер проверяет черновик и публикует его вручную; сервис не публикует карточки самостоятельно.

## 2. Входные данные

Сервис принимает JSON через HTTP API или те же поля через простую веб-форму. Оба способа используют одинаковые правила проверки и генерации.

- `name` — обязательная непустая строка с названием товара.
- `manufacturer` — обязательная строка; может быть пустой.
- `description` — обязательная строка с описанием или вставленным текстом/фрагментом технического паспорта; может быть пустой.
- `specs` — необязательный объект с произвольными ключами и строковыми значениями либо строка `«данных нет»`. Если поле отсутствует или объект пуст, характеристики считаются неизвестными. Пустое значение характеристики означает, что для этого ключа данных нет.

Загрузка и распознавание PDF и других файлов не входят в первую версию.

### Пример входного JSON

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

## 3. Что должен делать сервис

1. Принимать и проверять данные товара через JSON HTTP API или веб-форму.
2. Передавать сведения выбранному LLM-провайдеру для подготовки черновика.
3. Возвращать результат как JSON или Markdown, удобный для копирования.
4. При неполных данных формировать частичный черновик и явно отмечать неизвестные значения маркером `«данных нет»`; не добавлять отдельный список пропущенных полей.
5. При некорректном вводе, ошибке провайдера или невозможности сформировать результат, соответствующий требованиям, возвращать понятную ошибку, а не невалидный результат как успешный.

## 4. Состав карточки

JSON результата содержит следующие поля:

```json
{
  "seo_title": "SEO-заголовок",
  "seo_description": "SEO-описание",
  "search_queries": ["запрос 1", "запрос 2", "запрос 3"],
  "commercial_block": "Краткий текст для менеджера.",
  "name": "Название товара",
  "manufacturer": "Производитель или «данных нет»",
  "specs": {
    "характеристика": "значение или «данных нет»"
  },
  "description": "Исходное описание без изменений"
}
```

Если характеристики отсутствуют, `specs` в результате содержит строку `«данных нет»`. Если у переданной характеристики пустое значение, ключ сохраняется, а значение заменяется на `«данных нет»`. Пустой `manufacturer` также заменяется на `«данных нет»`. Поле `description` копируется из входа без изменений. Поля `warnings` и `missing_fields` в результат не включаются.

Требования к сгенерированным полям:

- SEO-заголовок — не более 70 символов, включая пробелы.
- SEO-описание — от 800 до 1200 символов включительно, включая пробелы.
- Структурированные характеристики сохраняют произвольные названия ключей и технические значения из входа.
- Поисковые запросы — от 3 до 5, сформированы только на основе входных данных.
- Commercial-блок — краткий текст для менеджера о применимости прибора и задачах, которые он решает; фиксированный лимит объёма не задаётся.

Генерируемые формулировки могут иметь грамматические и стилистические изменения, если исходный смысл сохраняется. Перефразирование, меняющее смысл, а также внешние или выдуманные сведения запрещены. Утверждения о применимости, аудитории и задачах должны опираться на входные данные. Если данных недостаточно для правдивого результата в требуемом формате и объёме, сервис возвращает явную ошибку.

## 5. Форматы ответа

- JSON — формат ответа API по умолчанию.
- API может вернуть Markdown по явно заданному параметру формата.
- Веб-форма позволяет выбрать JSON или Markdown.
- Markdown представляет те же поля карточки и не добавляет сведений, отсутствующих в JSON.

## 6. Технические и операционные требования

- Язык разработки — Python; веб-фреймворк — FastAPI.
- Приложение запускается локально и доступно только через `localhost`. Учётные записи, доступ по локальной сети и совместная работа нескольких пользователей не требуются.
- Используется один LLM-провайдер; конкретный провайдер выбирается при реализации. Настройки подключения, endpoint и API-ключ задаются через `.env`; файл `.env` должен находиться в `.gitignore`.
- Приложение само не сохраняет входные данные и результаты, не ведёт историю карточек и не требует базы данных.
- В интерфейсе сообщается, что введённые данные отправляются LLM-провайдеру. Сервис не обещает и не контролирует политику хранения данных провайдером.
- Полноценная CMS, админ-панель, автоматическая публикация, загрузка файлов, облачное развёртывание и поддержка нескольких LLM-провайдеров не входят в первую версию.
- Код должен корректно обрабатывать некорректный JSON, пустые допустимые поля и ошибки API провайдера. Секреты не хранятся в исходном коде.

## 7. README

В корне проекта нужно создать `README.md` с инструкцией по установке и запуску. Эта задача выполняется последней, когда проект будет полностью готов к релизу, все тикеты будут закрыты.

## 8. Принцип достоверности

Не добавляйте характеристики или иные сведения о приборе, которых нет во входных данных. При недостатке данных используйте `«данных нет»` там, где это применимо. Не подменяйте ошибку генерации карточкой, которая выглядит успешно сформированной, но нарушает требования.
